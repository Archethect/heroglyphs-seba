## Findings

[90] **1. Public token donations block the legacy handoff**

`LegacyProtocolPrincipalHandoff._conversionsClear` · Confidence: 90 · seen in 3/3 runs · NEW

**Description**
An attacker can send dust to the old manager or inactive router. The unconditional zero-balance checks make every subsequently approved handoff fail even after a new exact-ETH snapshot. This is a migration-availability issue, not theft.

**Fix**

```diff
- _configuration.oldRouter.balance != 0 ||
- IERC20(BOLD).balanceOf(oldManager) != 0 ||
- IERC20(SBOLD).balanceOf(oldManager) != 0 ||
- IERC20(BOLD).balanceOf(_configuration.oldRouter) != 0
+ _configuration.oldRouter.balance > _configuration.maximumRouterEth ||
+ IERC20(BOLD).balanceOf(oldManager) > _configuration.maximumOldBold ||
+ IERC20(SBOLD).balanceOf(oldManager) > _configuration.maximumOldSBold ||
+ IERC20(BOLD).balanceOf(_configuration.oldRouter) > _configuration.maximumRouterBold
+ // Pin reviewed residual caps in the immutable Safe-approved configuration.
+ // Emit exact observed balances after the successful handoff.
+ // Retain zero pending conversions, no active order, zero live claims, and exact ETH import.
```

Alternative suggested by some reviewers: remove these balance checks entirely, treating all stranded tokens as disclosed surplus. The approved bounded-cap approach retains an explicit abort/reapproval gate when observations exceed the Safe-approved limits.
